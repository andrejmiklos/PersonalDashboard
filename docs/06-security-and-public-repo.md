# 06 — Security & Public Repository Hygiene

The repository is **public**. The deployed Worker is reachable from the internet and proxies personal
calendar and task data. Both facts drive this document.

## 1. Threat model (summary)

| Threat | Mitigation |
|---|---|
| Secrets committed to git | `.gitignore`, secret templates only, gitleaks pre-commit + CI, GitHub secret scanning + push protection |
| Stranger calls the API and reads events/tasks | Bearer tokens on every `/api/v1/*` route; tokens ≥ 256-bit random; only hashes stored |
| Stolen device token (tablet) | Role `device` is limited (read data + complete tasks + heartbeat); revoke in admin; rotate |
| Stolen admin token | Stored only on owner's phone/PC; rotate via CLI script; short docs on how |
| Brute-force of tokens | 256-bit tokens make it infeasible; plus Cloudflare rate-limiting rule and constant-time comparison |
| Provider refresh tokens leak from DB | Encrypted (AES-GCM) with a key that lives only in Worker secrets |
| OAuth CSRF / code injection | Single-use `state` + PKCE, 10-minute TTL, admin-initiated |
| XSS in admin/display (calendar titles, task names, quotes) | All external text inserted via `textContent`; no `innerHTML` with data; strict CSP |
| Personal data in logs/caches | Never log event/task content; data endpoints `Cache-Control: no-store`; Cache API holds only short-TTL normalised payloads |
| Supply chain | Lockfile committed, Dependabot, few dependencies, `npm audit` in CI |

## 2. Roles and permissions

| Role | Token holder | Allowed |
|---|---|---|
| `device` | Tablet | `GET /display/state`, `GET /data/*`, `PATCH /tasks/:listId/:taskId` (complete/uncomplete only), `POST /display/heartbeat` |
| `admin` | Owner (phone/PC) | Everything, incl. layouts, schedule, settings, accounts/OAuth, tokens, overrides |

Accepted residual risk: a leaked device token can read the same data the tablet shows and toggle task
completion. It cannot change layouts, settings, accounts, or read other data.

Token format: `dsh_<role>_<43 chars base64url of 32 random bytes>` (prefix helps secret scanners and humans).
Generated by `npm run token:create -- --role device --label "kitchen tablet"` which prints the token once and
stores only `SHA-256(token)` in D1. Delivery: admin token typed/pasted into the admin login screen
(stored in the admin browser's `localStorage`); device token opened once on the tablet as `/display/#t=…`, then kept in Chrome's `localStorage`.

Auth middleware: parse `Authorization: Bearer …` → hash → lookup (not revoked) → compare with
`crypto.subtle.timingSafeEqual`-style constant-time compare → attach `{ role, tokenId }`. Update
`last_used_at` at most once per minute per token.

### 2.1 Display pairing codes

Typing a 55-character device token on the tablet is error-prone, and sending it to the tablet through a
chat or e-mail service would hand it to a third party. Displays therefore pair with a one-time code:

1. The owner runs `npm run pair -- --remote` (D1 access via wrangler, like the token CLI). It prints a code
   such as `K7QM-2XPA`: 8 symbols from a 31-letter alphabet without look-alikes (~40 bits), generated with
   the CSPRNG using rejection sampling. Only its SHA-256 is stored (`pairing_codes`).
2. The code is valid for **10 minutes, once**; creating a new code deletes any other unused code, so at most
   one is active.
3. The display (not paired, or its token rejected) shows a code field and calls `POST /api/v1/display/pair`
   (no token; body limit and Origin check apply). In **one D1 batch** the server checks the code, inserts a
   new device token and marks the code used, so a code can never yield two tokens.
4. Every failed attempt (wrong, expired, malformed) increments `failed_attempts` of the active code; after
   **10 failures** it stops working. With ~8.5·10¹¹ codes an attacker's chance before the lock is ~10⁻¹¹.
   All failures get the same `400 invalid_code`.
5. The token goes only to the tablet in the HTTPS response and is stored in `localStorage`; it is never
   displayed. An attacker can at worst lock the current code (create a new one).

The `#t=<device-token>` link still works as a fallback.

## 3. Secrets inventory

| Secret | Purpose | Where it lives | In git? |
|---|---|---|---|
| `GOOGLE_CLIENT_ID/SECRET` | Google OAuth client | Cloudflare secrets; `.dev.vars` locally | **No** |
| `MS_CLIENT_ID/SECRET` | Microsoft OAuth client | Cloudflare secrets; `.dev.vars` locally | **No** |
| `TOKEN_ENC_KEY` | AES-GCM key (32 bytes base64) for refresh tokens | Cloudflare secrets; `.dev.vars` locally | **No** |
| Admin / device tokens | API access | Owner's password manager, tablet Chrome `localStorage`, admin browser; hashes in D1 | **No** |
| Refresh tokens | Provider access | D1 `accounts` (encrypted) | **No** |
| Cloudflare API token (only if CI deploy is added later) | Deploy | GitHub Actions secret | **No** |

Committed templates: `.dev.vars.example` (keys only, dummy values), `wrangler.example.jsonc`.
Real `wrangler.jsonc` (account id, D1 database id, route) is **git-ignored**.

## 4. Personal data that must stay out of the repo

- Real location/coordinates, home address, city-level info in code or docs (use placeholders; docs may say
  "your city").
- The owner's Worker hostname / `workers.dev` subdomain, account id, D1 database id.
- Calendar names, event titles, task titles, email addresses, account ids — including in tests, fixtures,
  screenshots and issue text. Fixtures must be **fictional**.
- Real layouts exported from the editor (they reference source ids and may contain countdown labels like
  "Anna's birthday"). Only sanitised samples go to `examples/`.
- The git identity: use the GitHub `noreply` e-mail for commits
  (`git config user.email "<id>+xmiklosa@users.noreply.github.com"`) and enable
  "Block command line pushes that expose my email" in GitHub settings.
- Tablet identifiers, IP addresses, Wi-Fi names.

## 5. Repo safeguards (set up in Phase 0/1)

1. `.gitignore` covers `.dev.vars*`, `.env*`, `wrangler.jsonc`, `.wrangler/`, `*.local`, `node_modules/`,
   build output, `*.pem/*.key`, exported layouts (`layouts-export/`), IDE folders.
2. **gitleaks** as a pre-commit hook (husky or `pre-commit`) and as a GitHub Action on every PR/push.
3. GitHub → Settings → Code security: enable **Secret scanning** and **Push protection**, Dependabot alerts
   and updates.
4. Branch protection on `main` (optional for solo work): require CI green.
5. If a secret ever reaches git history: **rotate it first** (revoke in Google/Microsoft/Cloudflare), then
   clean history — never rely on deletion alone.
6. PR/commit review checklist item: "no personal data, no secrets, no real hostnames".
7. `SECURITY.md`: how to report vulnerabilities (GitHub private reporting).

## 6. Web hardening

- Response headers on all HTML: `Content-Security-Policy: default-src 'self'; img-src 'self' data:;
  style-src 'self' 'unsafe-inline'; script-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'`;
  `X-Content-Type-Options: nosniff`; `Referrer-Policy: no-referrer`; `Permissions-Policy` minimal.
  (Old Chrome ignores unknown directives; verify the display page still works with CSP in Phase 0/1.)
- Static files get these headers from `apps/worker/public/_headers`. Worker responses (JSON, redirects) get
  Hono `secureHeaders` with `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'`.
- API responses: `Cache-Control: no-store`, JSON only, uniform error shape without internals.
- `/display/` and `/admin/` static shells are public but contain **no data and no secrets**.
- The device token in the URL hash is never sent to the server, is removed from the address bar after
  first load, and is kept in `localStorage`. Do not put the token in a query string.
- Cloudflare: enable a rate-limiting rule (free tier allows one) for `/api/*` and `/oauth/*`; bot fight
  mode is not required.
- Input validation: zod for every body/param; size limits; reject unknown fields.
- CORS: none (same-origin). Reject `Origin` headers that do not match on state-changing requests.
- Logging: structured, without tokens/PII; `wrangler tail` only for debugging.

## 7. Token & key rotation (runbook outline)

- **Device/admin token:** create new → open `/display/#t=<new>` on the tablet / update admin browser → revoke old token
  (`npm run token:revoke -- <id>`).
- **`TOKEN_ENC_KEY`:** script `scripts/rotate-enc-key.ts` decrypts all refresh tokens with the old key and
  re-encrypts with the new one in one D1 batch; then `wrangler secret put`. (Implement in Phase 7.)
- **OAuth client secrets:** create a new secret in the provider console → `wrangler secret put` → delete the old.
- **Compromised provider account:** revoke the app in the provider's account security page, delete the account row
  in admin, reconnect.

## 8. Privacy notes

- Data flows: Google/Microsoft → Worker → tablet. Nothing else receives it. Open-Meteo receives only
  rounded coordinates.
- Cloudflare processes the traffic as the host; use of Cloudflare is an accepted trade-off (D-01).
- Cache API entries expire within minutes; D1 stores no event/task content (only config and encrypted tokens).
